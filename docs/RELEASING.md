# Releasing Aletheia — every stable version ships a VMware package, pushed to GitHub

**Policy (REQ-REL-001, from v0.1.0 on):** a stable version is a git tag `vX.Y.Z` on `main`. Every
such tag MUST produce the x86-64 VMware package and PUBLISH it as release assets on that tag in
GitHub. No stable version exists without its package; no package is published without having
booted from its own disks first.

## What a release is

| Artifact | Contents |
|---|---|
| `aletheia-vX.Y.Z-x86_64-vmware.zip` | `aletheia-x86_64.vmx` + `aletheia-x86_64.vmdk` (the interactive console — the OS you sit in front of), `aletheia-x86_64-selftest.vmx` + `aletheia-x86_64-selftest.vmdk` (boots, proves every invariant suite on the serial log, prints `[e2e] PASS`, halts), `README.txt`, `SHA256SUMS`, `verify-selftest-boot.log` (the boot log the packager itself produced from the packaged VMDK) |
| `aletheia-vX.Y.Z-x86_64-vmware.zip.sha256` | the zip's digest |
| `SHA256SUMS` | per-file digests of every file in the zip, the boot log included (computed after the boot, so it covers what shipped) |
| release notes | generated by the packager: commit, verification verdict, digest, the maturity caveat |

**x86-64 hosts only.** There is no arm64 VMware image: VMware Fusion on Apple Silicon runs arm64 guests
and cannot boot these disks; the aarch64 kernel targets QEMU's `virt` machine (`docs/BOOT.md`).

Both disks are GPT with a real EFI System Partition (`kernel-x86_64/scripts/mkesp.py`, deterministic
— the same commit yields byte-identical images), converted to VMDK with `qemu-img`. UEFI firmware
only, never legacy BIOS. The `.vmx` files are the repository's `kernel-x86_64/aletheia-x86_64.vmx`
with the disk, name and serial-log fields set for the package.

## How it is built, verified and pushed

1. `scripts/release-vmware.sh --version vX.Y.Z` builds both release kernels, writes both images,
   converts them, stages the package, then **boots the packaged VMDKs under QEMU+OVMF**: the
   selftest disk must exit 33 with `[e2e] PASS` on its serial log, the interactive disk must reach
   `aletheia> `. A host without QEMU/OVMF gets a loud `SKIP` of the verify step and the release
   notes say **UNVERIFIED** — never a silent pass.
2. `.github/workflows/release.yml` runs that script on every `vX.Y.Z` tag push (and on manual
   dispatch for an existing tag), keeps `dist/` as a workflow artifact, and publishes the zip, its
   digest and `SHA256SUMS` as **GitHub release assets** on the tag (`gh release create` if the
   release does not exist, `gh release upload --clobber` so a re-run replaces, never fails).
3. The main pipeline (`.github/workflows/ci.yml`, job `release-package`) runs the same script with
   `--version dev` on every push, so the packaging path is gated like every other gate script
   (`scripts/check-ci-parity.sh` refuses a script CI does not run).

## Cutting a stable version

```bash
# on main, green CI, versions in Cargo.toml already say X.Y.Z
git tag -a vX.Y.Z -m "Aletheia vX.Y.Z"
git push github vX.Y.Z               # push THE tag (never --tags: a stray local tag would publish too)
gh run watch                          # wait for "Release (VMware package -> GitHub release assets)"
gh release view vX.Y.Z                # the zip, .sha256 and SHA256SUMS are attached
```

Fallback, ONLY if the workflow failed (never in parallel with it — two publishers racing on one tag
is how a half-uploaded release happens): run `scripts/release-vmware.sh --version vX.Y.Z` on a host
with QEMU+OVMF, then `gh release create vX.Y.Z --verify-tag --notes-file dist/RELEASE-NOTES.md` (if the
release does not exist) and `gh release upload vX.Y.Z dist/*.zip dist/*.zip.sha256 dist/SHA256SUMS --clobber`.
The images are deterministic, so a later re-run of the workflow replaces the assets with identical bytes.

## What a version number claims

`vX.Y.Z` is a claim about GATES, not about maturity: it says the commit passed every job in
`ci.yml` and that the package booted from its own disks before publishing. It does NOT say the
system is production-ready — `docs/MATURITY.md` grades every subsystem and says plainly that
nothing here is; the release notes repeat that sentence on purpose. `v0.1.0` is the first stable
version: the composed desktop meets real input hardware (ADR-080) on a kernel that boots on three
CPU targets and proves its invariants on every boot.
